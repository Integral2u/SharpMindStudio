Projects

Work mode

Work gives a model project context and a small set of scoped tools. The model can read, search and edit only what the project allows, and every permission is explicit.

What Work is

  • A project folder with its own system prompt, memory, skills and runs.
  • Context locations with read, write and delete permissions.
  • A web permission that is off until you enable it.
  • A send gate: if the tool probe fails, the project cannot quietly run tools.
  • Works with a local model or a remote router (OpenRouter, EuroRouter, OpenCode Go). A Compute host is inference-only, so it cannot run Work tools yet.

Create a project

  1. Work → New project. Give it a name and a folder. The folder is the project's boundary. New chat sits next to it and starts a blank session in the open project.
  2. Write the system prompt. Say what the project is for, what the model may change and what it must not touch.
  3. Pick a provider. A local model is best for private files and reliable tool calls; a remote router works when the local model is too small. A Compute host is inference-only for Chat and cannot run Work tools yet.
  4. Add context. Point at the folders and files the project actually needs. Start read-only.
  5. Enable write/delete only after a read run. The permission is per location, not global.

Sessions and names

Sessions belong to the project that stores them. Chat lists the default project's conversations. Work lists every project that has work sessions, each as a collapsible group with a count. Opening a session from another group switches to that project first. Rename, delete and clear stay on the current project because they edit the live session store. A new session keeps the provider and model of the last chat, so switching projects does not quietly drop you back to a local model. If the saved remote key was deleted, Studio falls back to local.

The assistant's name follows the CUI convention. The sampling temperature selects a Greek tier: Alpha (cool) through Gamma to Epsilon (hot), and a session with no explicit temperature is Delta. The name is shown above each reply and given to the model in its system prompt. Temporary sub-agents keep the {Deity}-{Tier} form, such as Athena-Alpha.

Context and permissions

Paths outside the declared context are not reachable through the project tools. The project folder itself is not a substitute for an explicit context location.

Tool permissions

Every tool has four states. Off removes it from the prompt, so the model never sees it. Never keeps it visible but refuses every call without asking. Ask prompts, and Always permits. Each group header carries the same control and applies one value to every tool in that group, which is the quickest way to stop all writes at once.

A tool inherits from the model, family, project and Studio defaults, and each layer can override the one above it. Project, family, model and session also offer Inherit, which clears that layer's override and lets the next layer decide. Studio defaults have no layer above them, so they offer only the four values. A folder set to Never is a hard boundary and refuses the call whatever the tool says; otherwise the tool's own state decides, so Always is not silently downgraded by a folder that only asks. A delegated agent may be configured more permissively than the session, but that difference always raises a prompt and is never remembered.

Project settings save as you change them, and sending a prompt hides the panel so the conversation is what you see. A new project starts with a default context at its root, so the file tools work before the settings have ever been opened.

Command line

Work can run CLI tools through typed wrappers and a small, shell-shaped command line called the softshell. Both use the same project allowlist in Work project → Command line: add an executable such as git, dotnet, rg or curl, or start from a preset. An entry can also be a friendly alias with fixed leading arguments. Removing the entry removes the capability; an empty list leaves both the softshell and the wrappers unregistered.

The softshell parses familiar syntax itself and starts each program directly: pipes (|), output and input redirection (>, >>, <, 2>, 2>&1), &&, ||, ;, cd, pwd, echo, mkdir, rmdir, rename, inline NAME=value and $VAR. It never starts PowerShell, cmd or bash. Command substitution, backticks, here-docs, background jobs and globbing are refused with a readable message rather than approximated; quote an argument to pass *, ? or [ literally. Shells are never allowed, and an interpreter such as Python or Node needs the interpreter flag on its entry. Windows .cmd, .bat and .ps1 shims are refused as well, because launching them would start cmd or PowerShell; allow the native executable instead.

Pipes are buffered between stages, so a later stage starts with the complete output of the previous one. Redirection targets must stay inside the project contexts and go through the Read or Write gate. A redirect outside those locations is refused. The whole command shares one timeout, and a timeout kills the process tree.

mkdir (with -p), rmdir and rename manage directories without starting a program. mkdir needs Write; rmdir needs Delete; rename needs Delete on the source and Write on the destination. rmdir only removes an empty directory, and rename only moves directories.

The working directory belongs to the Work session. cd persists across RunShell calls, a new session or a new project starts at the project root, and deleting the directory falls back to the root. The Command line panel shows the shell directory and offers Reset. Wrappers and RunProcess start in that directory too, unless the call names another workingDirectory; that override applies to one call and does not replace the session directory.

Command access is layered: System → Project → Family → Model → Session. System chooses Restricted or Unrestricted; every layer below can inherit the parent, or choose either mode. The nearest layer wins, so a lower layer may widen or narrow the parent. Restricted runs only the effective allowlist, and an empty list refuses every external command, including RunProcess. Unrestricted ignores the allowlist and lets RunProcess start any program. The softshell stays off in Unrestricted because its boundary is the allowlist; the CLI wrappers remain available when installed, and each one can still be turned off under Enabled tools. Switching to Unrestricted asks for confirmation. Unrestricted removes the allowlist only: the RunProcess tool permission and the context's Run permission still apply.

Allowlists inherit down the same chain. A lower layer can add commands for its own scope and disable commands it inherited, but a command disabled above cannot be re-enabled below. When the same name appears more than once, the nearest definition wins. Each command row has Disable, Ask, Allow and Allow Always: Ask prompts on every run, Allow skips prompts for the rest of the app session, Allow Always persists, and Disable removes the command. A local override offers Inherit to return to the parent definition. The editors live in Settings → System, the project Command line panel, the Family and Model tabs, and the session tool panel.

An allowlist entry alone is not enough: RunShell and the wrappers also need the context's Run permission and a tool permission of Ask or Always. If either is Never, the call is refused before the program starts. The Project Command line panel warns when a gate is blocking and offers Set command tools and Run to Ask. New projects start with Run = Ask on the default context, so the first command prompts instead of being refused.

Curated wrappers take precedence over the generic shell when the matching executable is allowed: git_status, git_diff, git_log, dotnet_build, dotnet_test and rg_search. They use argv rather than the parser and are the better choice for routine repository, build and search work. RunProcess follows the same mode: Restricted requires an allowlist entry, while Unrestricted can start any program.

Secrets in commands

A command can use a named secret from Settings > Vault as %vault:NAME%. This works in RunProcess, the softshell, a CLI wrapper, an MCP server command, argument or environment value, and an MCP tool argument. Studio expands it after the arguments are split and before the process or request starts, so a value with spaces stays one argument. The permission prompt shows the reference and the secret name, never the value. A missing name refuses the command instead of passing the literal reference, and the value is removed from stdout, stderr and a timeout message.

Redaction is best effort: a program that encodes, splits or transforms the value can defeat it. The permission gate is the real control, so use Ask for anything that can reach the network, and do not give an untrusted model or plugin Always.

Skills

Skills are reusable instructions with a name, description and body. They can be global or overridden per project. Use them for repeatable procedures: review a dataset, prepare a model card, run a release checklist.

  • The skill list shows the effective source (global or project).
  • A skill can be previewed before it is used.
  • Skills do not grant permissions; the project's context locations still decide what tools can touch.

The work loop

  1. Ask for the outcome, not the exact keystrokes. Mention constraints and files.
  2. The model proposes tool calls; Studio shows them and applies the permission gate.
  3. Review file changes in the session before accepting destructive work.
  4. Keep the useful decisions in the project memory so the next session starts informed.
  5. Use runs and the project's models folder for artifacts you want to keep.
Files, then programs. Work can list, read, search, create, write, append, edit and delete files, and fetch a page when the project allows it. Edit replaces one exact piece of text, so it can insert, change or remove a section without rewriting the whole file; it refuses ambiguous text instead of guessing. RunProcess can start a program in an allowed folder once that folder's Run permission is Ask or Always; it is Never by default, passes arguments without a shell, and kills the tree on timeout. It runs real code with your account's permissions, so Studio gates the command, not everything the program touches. Keep Command access on Restricted unless you deliberately need to run unlisted programs.

A SharpMind Compute host is currently inference-only for Chat. It does not expose Work's tool calling, so Work should use a local model or a remote router. Chat can use any of the three. OpenRouter, EuroRouter and OpenCode Go keep separate keys, base URLs and model lists, so Work can switch between them without re-entering a key. A new session starts on the router used last.

Tool-call recovery. Studio can be strict, lenient or loose about malformed tool calls. A small local model may need Lenient; a hosted model is usually fine with Strict.

Safety

  • Start with read-only context. Add write after the model has shown it understands the project.
  • Leave delete off for source trees, model folders and anything under version control.
  • Keep secrets out of context locations; the model can read every file it is given.
  • Keep Command access on Restricted. Unrestricted lets RunProcess start any program with your account permissions.
  • The send gate exists to stop a broken tool probe from becoming a silent failure. Fix the probe rather than bypassing it.
  • Review remote-model prompts: OpenRouter sees the conversation and any tool output you send.
